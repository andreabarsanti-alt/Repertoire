# CLAUDE.md

## Project Overview

Repertoire is a single-page web app for managing a musical repertoire. It runs on an iPad via GitHub Pages with no backend or build step required.

## Architecture

- **Single-file app**: Everything (HTML, CSS, JavaScript) is in `index.html`
- **No build step**: Plain vanilla JS, no frameworks or transpilation
- **Storage**: Uses `localStorage` for persistence; seeds from a per-profile JSON file on first load
- **Hosting**: Static files served via GitHub Pages from `main` (the app, plus `request.html`, the separate audience song-request page — see "Audience requests")
- **Data branch**: the profile JSON files live on a separate `data` branch (`DATA_BRANCH`), not on `main`, so data pushes from the app never clutter the app's history. `SEED_FILE` is therefore not a same-origin file next to `index.html`: every read — first-load seed in `boot()`, the startup repo check, 🔄 Refresh, ⬇ Pull — goes through `fetchRepoData(cfg?)`, which GETs the file from the GitHub Contents API (raw media type, `?ref=<branch>`, `cache: 'no-store'`). With a saved token it uses the configured owner/repo/branch/path, authenticated; without one it reads `DATA_BRANCH` of the public repo anonymously (owner/repo from the `<owner>.github.io` host, else `DATA_REPO_FALLBACK` for local testing), falling back to `raw.githubusercontent.com` if the API refuses (anonymous rate limit). It returns `null` for a 404 (a new profile not yet pushed). ⬆ Push PUTs to the configured branch, which defaults to `data`; `getGithubConfig()` silently migrates any saved config still on `branch: "main"` (from before the move) to `data`, since a push to `main` would recreate the JSON there.
- **Profiles**: `?profile=<name>` in the URL (default `two_of_us`) namespaces both the `localStorage` key and the seed filename — `repertoire_<name>.json` (e.g. `repertoire_two_of_us.json`, `repertoire_loose_ends.json`). Since `PROFILE` always falls back to `two_of_us` when unset, there is no bare `repertoire.json` — the pre-multi-profile file was retired (deleted from the repo) once nothing read it. Seed, Refresh, repo-sync check, Push/Pull, and Export all use the same per-profile `SEED_FILE` (on the `data` branch — see "Data branch"). The header's `#profile-select` dropdown switches between them via `switchProfile()` — just a `location.search` navigation, since each profile is a fully separate `STORAGE_KEY`/`SEED_FILE`/`GH_CFG_KEY`, not something to swap live in place.
- **Profile registry**: which profiles exist at all (id + display name) lives in `localStorage['rep_profiles']` (`PROFILES_KEY`, read/written via `getProfiles()`/`saveProfiles()`) — deliberately *not* namespaced by `PROFILE` like everything else, since it's the one list every profile's page load needs to see. Falls back to `DEFAULT_PROFILES` (`two_of_us`/`loose_ends`) if empty, so existing bookmarks keep working untouched. `renderProfileSelect()` rebuilds the dropdown's `<option>`s from it on every `boot()` (plus a trailing `✎ Edit profiles…` entry) — if the URL's `?profile=` isn't in the registry (a hand-typed one-off), it's shown unpersisted rather than left blank. Picking `__manage__` is intercepted in `switchProfile()` before the normal navigation and opens `#profiles-modal` (`openProfilesModal()`) instead, where `addProfile()` slugifies the typed name into an id (de-duped against collisions) and `deleteProfile()` removes the registry entry plus that profile's `rep_v2_<id>`/`rep_github_config_<id>` localStorage — a confirm() first, and it only ever touches local data, never the repo's `repertoire_<id>.json`. A brand-new profile just starts with the default empty `db` (no seed file to fetch yet) until its first ⬆ Push creates one.
- **Header height is dynamic, not hardcoded**: the header wraps to a different number of rows depending on screen width (and whether the mobile ⋯ panel is open), so everything sticky-positioned below it (`#sync-banner`, `.sets-sidebar`, `.set-detail-header`) reads the `--hdr-h` CSS var instead of a fixed px offset. `syncHeaderHeight()` measures the real `<header>` and writes the var — called from `boot()` (plus once more after `document.fonts.ready`, since the async Google Fonts swap can nudge wrap height), from the debounced `resize` listener, and from `toggleHdrMore()`. Forgetting to call it after something that changes header content/height is exactly the bug this replaced — content used to disappear behind the sticky header on any screen where the header ran taller than the guessed 58px/76px.
- **Header ⋯ menu**: the `⋯` button (`#hdr-more-toggle` / `toggleHdrMore()`) shows at every width. Export and Import (`.hdr-more-file`) always sit behind it: above 600px (iPad) `#hdr-more` is `display:contents` (the tune toggles in `.hdr-toggles` and ● Start live sit inline in `.hdr-actions`), and opening ⋯ drops `.hdr-more-file` down as a small absolutely positioned menu under the header's right edge. `.hdr-actions` wraps (`flex-wrap`), and between 601–1000px (iPad portrait) `.hdr-toggles` gets `order: 1` so the three checkboxes wrap together onto the row below the buttons instead of stranding Push alone. A document click listener closes the menu on any tap outside `#hdr-more`/the toggle (not on taps inside it, so Import's file input isn't hidden mid-pick).
- **Mobile header (≤600px)**: everything in `#hdr-more` (tune toggles, Start live, Export, Import) folds behind ⋯ into a full-width dropdown panel (`.hdr-toggles`/`.hdr-more-file` become `display:contents` inside it). Title/profile/⋯+Refresh+Pull+Push stay on the primary row; the tab nav gets `order` bumped onto its own full-width row underneath.
- **Build stamp**: `APP_BUILD` (`'YYYY-MM-DD HH:MM'`, Italian time) is shown as "Build …" at the bottom of the header ⋯ menu (`#app-build`), so Andrea can tell whether a reload picked up the latest deploy. **Bump it in every commit that changes `index.html`.**
- **Text size**: `html { font-size: 110% }` scales every `rem` size in the UI (Andrea asked for slightly bigger fonts); `body` is 20px. The CRD reader/editor sheets use their own px sizes (A−/A+), so they're unaffected.

## Data Format

```json
{
  "songs": [
    {
      "id": "unique-id",
      "title": "Song Title",
      "tags": "Neil Young, rock, acoustic",
      "key": "G",
      "capo": "2",
      "harp": "G",
      "ugLink": "https://tabs.ultimate-guitar.com/...",
      "crd": "Am        C          G\nLyric line one...",
      "tryOut": false,
      "lyricsOnly": false,
      "autoSpeed": 20
    }
  ],
  "setlists": [
    {
      "id": "unique-id",
      "name": "Setlist Name",
      "type": "live",
      "liveType": "gig",
      "date": "2026-08-07",
      "items": [
        { "type": "section", "name": "Set 1", "collapsed": false },
        { "type": "song", "songId": "id1" },
        { "type": "section-end" },
        { "type": "song", "songId": "id2", "altSongId": "id5", "useAlt": false },
        { "type": "section", "name": "Encore", "collapsed": true },
        { "type": "song", "songId": "id3" }
      ]
    }
  ],
  "tuneUp": false,
  "chordsAsPlayed": true,
  "tuneKeyMemo": { "id1": "G#" }
}
```

- `tuneUp` (top-level, global): whether the "Half-step down tuning" header toggle is on. Flipping it (`toggleGlobalTune`, confirmed) moves every song's root `key` a semitone — down when turned on, up when turned off — and never touches `crd` or `capo` (E shapes, capo 3: G, or F# tuned down). Exactly reversible: `tuneKeyMemo` (top-level, `{songId: key}`) remembers each key as it was spelled before the last flip, so flipping back restores it byte for byte (`G#` → `G` → `G#`, not `Ab`) unless it was edited in between (`shiftKeyName`). Until 2026-11-26 it instead bumped every capo ±1 clamped at 0, which wasn't reversible (negative and 0 capos drifted).
- `chordsAsPlayed` (top-level): chord sheets are stored **as played** — the shapes, in the playing key (Andrea, 2026-11-26). Data without the flag (an old export/backup, old localStorage) stored each sheet in the root and had the reader transpose it on open; `migrateCrdPlayed(data)` rewrites those once into exactly what the reader showed and sets the flag (key/capo untouched). It runs in `migrateAll()` everywhere data is loaded (boot, first seed, Pull, Refresh, Import, Load from repo), and on the repo copy in the boot sync check. Both profiles' repo files were converted offline the same way (all 170 sheets render identically before/after), plus six roots corrected where the saved key didn't match the sheet (Blackbird, Nobody Knows You…, 59th Street Bridge Song, Starman, Il cielo è sempre più blu, The Sound of Silence); backup of the unconverted files on branch `data-backup-2026-11-26`. (A first attempt on 2026-11-22 converted the sheets but kept the old capo-bump math; it was reverted.)
- `setlist.type` is `'live'` (a real gig, rehearsal or soundcheck, has a `date`) or `'generic'` (a working list, no date). Drives the left-pane split — see "Setlists" below.
- `setlist.liveType` (live setlists only): `'gig'`, `'rehearsal'` or `'soundcheck'` (`LIVE_KINDS`). Missing/unknown reads as `'gig'` via `liveKindOf(sl)` — not backfilled on load, so pre-existing live setlists (all gigs) stay byte-identical and don't trip the repo-sync banner. Removed together with `date` when a setlist is un-marked Live.

- `song.tryOut` (boolean, default off; labelled **❓ Not ready** in the UI — renamed from "Try out" by Andrea, field name unchanged so data stays compatible): a checkbox on the song itself, settable from the Songs tab row (`toggleSongTryOut`), its add/edit modal, its inline edit row, or a setlist row's ✎ edit. Marks it as out of the repertoire for now — the Songs tab's repertoire-scope filter reads it (`songsScopeFilter`, see below); there's no dedicated setlist or view built on top of it beyond that.

- `song.lyricsOnly` (boolean, default off): a 🎤 checkbox next to Try out in the same places (Songs tab row `toggleSongLyricsOnly`, Add Song modal `f-lyrics`, inline edit `ie-lyrics`, setlist ✎ edit `sl-ie-lyrics`; a "🎤 Lyrics only" chip via `kchBadges`). When on, the CRD reader shows lyrics and section labels only: `renderCrdHTML(text, semis, lyricsOnly)` first runs `lyricsOnlyText`, which drops every chord line (`isChordLine`), strips inline `[G]` chords out of lyric lines, and drops a line left empty by that. Display only — `s.crd` keeps its chords (the full editor's preview still shows them).

- `song.autoSpeed` (optional number, 5–60 in steps of 5): the song's own auto-scroll speed in the CRD reader. Written automatically by `crdAutoSpeedStep` whenever the speed changes while that song is open (toolbar −/+ or the pedal), and loaded by `openCrdReader` (`crdSnapSpeed`); songs without one always start at the fixed `CRD_AUTO_SPEED_DEFAULT` (20). (It briefly fell back to the last speed used on the device; Andrea wanted a fixed 20.) Part of `db`, so it's saved, exported and pushed/pulled like any other song field.

- `song` items resolve to `altSongId` instead of `songId` when `useAlt` is true — lets a slot's live song be swapped without reordering.
- `section` items are collapsible chapter headings that live inline in the same flat `items` array — every `song` item after one belongs to it by position (not by any nested/reference structure) up to the next boundary: another `section`, an explicit `section-end`, or the end of the list. `collapsed` just controls whether those rows are rendered; it never changes what plays, prints, or counts.
- `section-end` items are an invisible boundary marker with no other fields — they close a section early instead of letting it run to the next header. See "Sections" below.
- Legacy setlists with a flat `songIds: [id, ...]` array are migrated to `items` on load (`migrateSetlists()`), which also silently drops any leftover `subset` items from the retired embed-another-setlist feature (replaced by `section`). The same pass backfills a missing `setlist.type` — `'generic'` by default, except a handful of known pre-existing gigs matched by name (`LEGACY_LIVE_DATES`) that get `'live'` plus their date, so setlists saved before the live/generic split still land in the right list.

## Key Implementation Details

- **Confirm every destructive action** (Andrea's standing rule, 2026-11-26): any clear, reset, remove or delete — songs, setlists, setlist rows/sections (`removeSlItem`), alternates (`clearAlt`), profiles, requests (Clear requests, 🗑), likes/visits Reset, Now playing Clear (`liveNowClear`), gig image, GitHub settings (`clearGithubConfig`) — asks with `confirm()` first. Keep it that way for anything new. Reversible marks (✕ dismiss a request, which has ↺) don't need one.

- **Theme**: Deep blue-black / muted teal (`#3d9e8c`) studio/DAW aesthetic
- **Song title links**: `songTitleLink(s, opts)` is the one shared fallback chain — CRD reader link (if `s.crd`) → Ultimate Guitar link (if `s.ugLink`) → plain text — used everywhere a title appears (Songs table, setlist rows, Play mode). `opts` covers each call site's own markup: `cls`, `plainTag` (wrap the plain-text fallback too, or leave it bare), `wrap` (additionally wrap the title text itself, e.g. `'strong'`), `crdStop` (stopPropagation before opening the reader), `ugOnclick` (raw onclick for the UG link, e.g. stopPropagation or Play mode's `playOpenedUG` flag).
- **No Visualizer tab**: the tag-bubble Visualizer tab (`renderBubbles`/`packBubbles`/`showDetail`) was removed (Andrea, 2026-11-26: not helpful); Songs is the default tab. `request.html` keeps its own separate bubble code.
- **Songs table**: Inline editing (click row or ✎ button); sortable columns — the second column is **Artist · Tags** (`sortCol = 'artist'`), sorting by `songArtist(s)` (a song's first tag, the same rule as the Add Songs picker's "Artists") then title, songs with no artist last; tag autocomplete dropdown on tags fields; toolbar has two independent dropdowns — chord sheet (`songsCrdFilter`: Any chords/🎸 Has chords/No chords, `setSongsCrdFilter`) and repertoire scope (`songsScopeFilter`: Any song/In repertoire/🧪 Try out, `setSongsScopeFilter` — "In repertoire" means NOT `tryOut`) — alongside the text search; all three apply together (AND) in `renderSongs()`. Both reuse the header's `.profile-select` dropdown styling rather than introducing new CSS. Each row's actions cell also carries a live `tryOut` checkbox (`toggleSongTryOut`) — same field as the modal/inline-edit checkbox, just a one-click path to it that doesn't require opening edit mode; `event.stopPropagation()` on its wrapping `<label>` keeps the click off `handleRowClick`'s "open inline edit" fallback
- **Quick UG Import**: Opened from the header's **📋 Paste UG** button (`#btn-paste-ug`, `pasteUGLink`, right after ● Start live so it's on screen whatever tab is open — inside the ⋯ panel on a phone; it replaced the Songs tab's old ⬇ UG button, Andrea): it reads a UG link from the clipboard (the UG app's Share → Copy link; `UG_LINK_RE` anywhere in the text), opens the dialog with the link filled in (`openUGImport(true)`, no focus so the iPad keyboard stays down), or toasts if there's no UG link. The dialog has editable **Title** (`ug-import-title`) and **Tags** fields, auto-filled from the link slug (`parseUGUrl`) or from the share text around the link (`ugShareMeta`: "<Title> [Chords/Official/…] by <Artist>", minus "Check out"/"on Ultimate Guitar" and quotes) — `dataset.auto` marks an auto-filled value, so a later link change refills it but never overwrites typing. The UG app's share link is often just `/tab/<id>` with no slug: `parseUGUrl` still accepts it (empty title/artist), a toast asks for the title, and Add Song refuses an empty Title. The dialog's full-width **📋 Paste chords** button (`pasteCrdInto('ug-import-crd')`) then takes the chords copied next; if the clipboard still holds the link it says to copy the chords first. Parses title and artist from a UG URL slug when there is one — no network request needed. Pattern: `/tab/{artist}/{title}-{type}-{id}`. The import dialog also has its own optional **Chord Sheet** box (`#ug-import-crd`, blanked on every `openUGImport`) for pasting the UG text as-is (no markup clean-up). The dialog itself carries **Key (root)** (`ug-import-key`), **Capo** (`ug-import-capo`, label `#lbl-ug-capo` follows Keyboard Mode via `capoWord()`) and **Not ready** (`ug-import-tryout`), all blanked by `openUGImport`. Its **Add Song** button (`quickAddUGImport`, also Enter in the link/tags field once a link parses) saves the song straight away — title, artist (or typed tags), key, capo, Not ready, UG link, chord sheet. (There used to be a **More details…** button opening the full Add Song form; Andrea replaced it with these fields, 2026-11-26.)
- **📋 Paste chords** (`pasteCrdInto(id)`/`tidyPastedChords`, `CRD_LINK_FIELD`, `UG_LINK_RE`): the app can't fetch UG pages (no CORS, and Andrea's paid sign-in lives in the UG app/Safari), so chords come over by copying them in the UG app (this works for Official tabs too) and tapping **📋 Paste** next to a Chord Sheet box — as the UG import dialog's **📋 Paste chords** (`ug-import-crd`), and next to the Chord Sheet box in the Add Song modal (`f-crd`) and both inline edits (`ie-crd`, `sl-ie-crd`). It reads `navigator.clipboard.readText()` and tidies the text (strips UG's `[ch]`/`[tab]` markup, CRLF, non-breaking and trailing spaces, runs of 3+ blank lines), asking before replacing a non-empty box. A short clipboard text containing a UG link (the UG app's Share → Copy link) goes into that form's UG link field instead (`ug-import-url` re-runs the title/artist preview). (A Safari bookmarklet route was built and reverted on 2026-11-26 — Andrea chose this one.)
- **Ultimate Guitar links**: Normalized to `tabs.ultimate-guitar.com` Universal Link domain for iOS app compatibility
- **CRD reader**: A song can carry a `crd` field — a plain-text chord/lyric sheet, entered manually (Add Song modal, inline edit, or the full-page editor). When a song has `crd`, its title everywhere (songs table, setlists, play mode, Live tab) opens the in-app CRD reader (`openCrdReader`) instead of the UG link. Because it's an in-page overlay rather than a navigation, it also sidesteps the AirTurn/UG Universal-Link app-switch issue during Play mode.
  - **Full-screen overlay** (`#crd-reader`), not a small modal. The header/toolbar (`.crd-chrome`) is tap-to-toggle — tapping the sheet hides it for more reading room, tapping again brings back the "← Back" button and controls.
  - **Chord detection**: recognizes chords either inline as `[G]` (ChordPro-style) or on their own "chord line" above the lyrics (a line where *every* token is a chord or decor). Chords are matched by a grammar (`CHORD_RE`, built from `CHORD_BODY`), not a fixed list: root `A–G` + optional `#`/`b`, optional quality (`m`/`min`, `maj`/`Maj`/`M`, `mmaj`/`mM`, `dim`/`°`, `ø`, `aug`/`+`), optional extension (`2 4 5 6 7 9 11 13`, `6/9`/`69`, optionally `M` for the Latin `7M` = maj7), any number of modifiers (`sus`/`sus2`/`sus4`, `add2/4/9/11/13`, alterations `b5 #5 b9 #9 #11 b13` incl. `+`/`-` forms, a bare `+` as in `C7+`, `no3`, `alt`, or a parenthesised group like `(b9)`/`(add9)`/`(maj7)`), and optional slash bass `/F#` — so `7sus4`, `D7sus4/A`, `m7b5`, `maj9`, `D6add9/F#`, `Dmadd11`, `A7M`, `G7(b9)` all parse while lyric words don't (the whole token must be a chord spelling). Spaced slash chords (`G / D`) are joined first; `tokenParts` keeps wrapping parens/commas outside the chord but keeps a chord's own closing `)` (`C(add9)`). Decor tokens that don't break a chord line (`CHORD_DECOR_RE`): bars `|`/`||`/`|:`, `%`, `N.C.`, beat slashes `/`, and repeat marks `x2`/`2x`. `[Verse]`/`[Chorus]`/`[Break]`/`[Fade Out]`/etc. (`SECTION_RE`) — or any non-chord `[label]` standing alone on its line, e.g. `[Guitar Solo]` — render as section labels, not chords. `transposeToken` only moves the root and a trailing `/bass` note (so `6/9` in the body is untouched) and knows `Cb`/`Fb`/`E#`/`B#`; Keyboard Mode doesn't touch chord spellings (it only relabels capo).
  - **Root key vs. Playing key**: `s.crd` is stored **as played** (the shapes — see `chordsAsPlayed`). One rule ties the fields together: **root = playing key + capo − (tuneUp ? 1 : 0)**. `s.key` is the root (sounding key), `s.capo` the fret clamped (Loose Ends: a keyboard transpose, can be negative), and the playing key is derived from them (`playKeyFor(s, tuneUp)` / `deriveDefaultTKey(s)`) — it's the key the stored sheet is in. The reader header shows two editable note-name inputs — **Key** (`crd-key-input` → `crdEditKey`, the root) and **Playing key** (`crd-tkey-input` → `crdEditTKey`) — plus a read-only **Capo** badge solving the rule for the capo (`computeCapo`, mod 12). On open, Playing key is the saved one and the sheet is shown as stored (no transpose). The forms' Key field is still the root; editing key or capo there doesn't touch the sheet, so keep them consistent with it (the reader is the place to change them together).
  - Key/Playing-key inputs accept a root note plus an optional quality restricted to `KEY_QUALS` (`''` major, `m` minor, `mmaj7` minor-major-7) — nothing else (`parseKeyName`/`formatKeyName`; e.g. `Am`, `F#`, `Gmmaj7` parse, `Am7`/`Csus4` don't). Only the pitch matters for the capo/transpose math, but `deriveDefaultTKey` and the −/+ steppers carry the quality through unchanged so e.g. an `Am` song defaults to (and steps between) minor playing keys, not major.
  - Editing **Playing key** (−/+ semitone steppers `crdTKeyStep`, ↺ `crdTKeyReset` back to the saved default, or typing directly) live re-transposes the on-screen chords (`crdChordsEff`, computed against the song's *actual saved* key, not any pending root edit) and updates the Capo badge. Editing **Key** (the root) only updates the Capo badge/preview — it never touches the displayed chords or the saved sheet until committed.
  - **Committing** (`crdCommit`, bound to `#crd-store-btn` "💾 Save"): enabled once the root or the playing key differs from what's saved (capos compared mod 12, `sameCapo`, so a stored −3 isn't "dirty" against a computed 9). A new playing key rewrites `s.crd` into the new shapes (`transposeCrdText` by `crdChordsEff`) and sets the capo that keeps the root; a new root alone keeps the sheet and only changes the capo. Reloading without saving reverts to what's saved. `crdUpdateStoreBtn()` keeps the enabled state in sync on every keystroke via the lightweight `crdMetaEdited` (which deliberately avoids rebuilding `#crd-meta`, to not steal focus mid-typing).
  - **Half-step tuning and the reader**: the toggle only moves `s.key`, so the shapes shown and the Capo badge stay the same; only the Key box changes.
  - **Keyboard Mode**: `keyboardMode` is a device-local display preference (`localStorage['rep_keyboard_mode']`, header checkbox `keyboard-mode-toggle`/`toggleKeyboardMode`) — not part of `db`, so it isn't JSON-persisted or pushed/pulled with the data. It relabels every "Capo N" as "Transpose ±N" wherever a capo value is shown (song badges via `kchBadges`, the CRD reader's badge, print sheets, the Add Song modal's field label, both inline-edit placeholders, and the 💾 Save confirms) via `capoWord()`/`capoText()`/`capoBadgeText()`/`capoWrap()`. The stored `s.capo` fret count never changes — only fret counts over 6 are *displayed* wrapped an octave down as the equivalent negative shift (capo 7 → Transpose -5 … capo 11 → Transpose -1), since that's the shift a keyboard player would actually play.
  - No delete button in the reader — deleting a song only happens from the Songs tab, so it's never one misplaced tap away while reading/playing.
  - **Full-page editor** (`#crd-editor`, `openCrdEditor`/`closeCrdEditor`): the "⤢ Full editor" button next to the CRD field (Add Song modal `f-crd`, Songs table inline edit `ie-crd`, or setlist inline edit `sl-ie-crd`) pops a full-screen editor — a single full-width raw textarea by default, with a "👁 Preview" header button (`toggleCrdEditorPreview`/`setCrdEditorPreviewing`) that swaps it for a live-rendered preview (same `renderCrdHTML` the reader uses, always at transpose 0 — i.e. the shapes as stored, no playing-key/capo math here), one full pane at a time rather than a permanent side-by-side split; the preview is only (re-)rendered at the moment you switch to it. It also carries just the root **Key** field (`crdEditorKey`), no Playing key/Capo — it works even for a not-yet-saved song (no `db.songs` entry to read) by deriving the sibling Key field id straight from `targetId` (`"f-crd"` → `"f-key"`, `"ie-crd"` → `"ie-key"`, etc.). On "← Done", the crd text *and* Key sync back into those sibling fields (`dispatchEvent('input')`, so the outer form/Save picks them up). Doubles as the fix for a sheet transcribed in the wrong key — edit the raw chords directly and update Key alongside them; no separate "re-root" tool needed (there used to be one in the reader itself, removed once this covered the same case).
  - **Keyboard**: Up/Down/PageUp/PageDown scroll the sheet, Escape closes the reader (ignored while typing in a text field). Each key press goes through `crdJump(dir)`, which jumps `crdScrollStep()` = **Scroll %** (`crdScrollPct`, toolbar −/+ in steps of 5, 5–100%, default 35, device-local `localStorage['rep_crd_scroll_pct']`) of the visible pane height. `crdJump` clamps the target to `[0, scrollHeight − clientHeight]` and does nothing at a bound, so scrolling stops at the start and end of the song; rapid repeats chain from the previous jump's target (`crdJumpTarget`, within 600 ms) instead of mid-animation positions, and `#crd-scroll` has `overscroll-behavior: contain`. (Plain smooth `scrollBy` could rubber-band past the edges on iPad Safari, letting a hold scroll backward "forever".)

- **Setlists**: Reordering via pointer-events drag, grabbing a row's ⠿ handle (`initDrag`/`startSlDrag`/`onSlDragMove`/`endSlDrag`/`cleanupSlDrag`, driven by the module-level `slDrag` state) rather than the HTML5 drag-and-drop API — `dragstart`/`dragover`/`drop` never fire from touch input on iPad Safari, this app's actual platform, so native DnD silently did nothing when grabbed on-device even though it worked with a mouse. Up is always a plain adjacent single-slot swap for a section header — whatever sits right before it can never have more of its own content trailing behind, since a section always auto-closes at the next header regardless (see the `section-end` note below), so there's nothing to strand. Down for a section header isn't: if what immediately follows is itself *another* section's header, a naive single-slot swap would leapfrog just that header and strand its songs behind with no header of their own — silently losing them out of any section (collapsed just hides the wreckage, it isn't the cause). - **Export**: downloads `db` as JSON named after the profile's `SEED_FILE` (e.g. `repertoire_two_of_us.json`), so an exported file matches the repo file it would replace
- **Force refresh**: The header's "🔄 Refresh" button (`forceRefresh`) is a manual, always-overwrites version of the same idea — refetches `SEED_FILE` from the `data` branch (`fetchRepoData`, uncached) right now and loads it unconditionally after a confirm, no GitHub token needed (it uses the saved one if there is one). It doesn't stop at the data — after saving the fresh JSON to `localStorage` it calls `hardReloadPage()`, which appends a `_hr=<timestamp>` cache-bust param and `location.replace()`s to it, forcing a real network refetch of `index.html` itself (everything — HTML/CSS/JS — lives in that one file, so a stale cached copy would otherwise keep serving old app code even with fresh data). `boot()` strips `_hr` back off the visible URL via `history.replaceState` on the way back in. Plain `location.reload()` isn't reliable enough for this, particularly in iPad Safari's "Add to Home Screen" standalone mode, which is more aggressive about caching and has no visible reload button at all.
- **Viewport fix**: Resets viewport meta on `visibilitychange` to prevent iPad Safari zoom-out on app resume
