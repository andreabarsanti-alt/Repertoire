# CLAUDE.md

## Project Overview

Repertoire is a single-page web app for managing a musical repertoire. It runs on an iPad via GitHub Pages with no backend or build step required.

## Architecture

- **Single-file app**: Everything (HTML, CSS, JavaScript) is in `index.html`
- **No build step**: Plain vanilla JS, no frameworks or transpilation
- **Storage**: Uses `localStorage` for persistence; seeds from a per-profile JSON file on first load
- **Hosting**: Static files served via GitHub Pages
- **Profiles**: `?profile=<name>` in the URL (default `two_of_us`) namespaces both the `localStorage` key and the seed filename — `repertoire_<name>.json` (e.g. `repertoire_two_of_us.json`, `repertoire_loose_ends.json`). Since `PROFILE` always falls back to `two_of_us` when unset, the *bare* `repertoire.json` is never actually fetched by the app — it's a pre-multi-profile leftover, kept in sync manually rather than something to seed real data through. The header's `#profile-select` dropdown switches between them via `switchProfile()` — just a `location.search` navigation, since each profile is a fully separate `STORAGE_KEY`/`SEED_FILE`/`GH_CFG_KEY`, not something to swap live in place.
- **Profile registry**: which profiles exist at all (id + display name) lives in `localStorage['rep_profiles']` (`PROFILES_KEY`, read/written via `getProfiles()`/`saveProfiles()`) — deliberately *not* namespaced by `PROFILE` like everything else, since it's the one list every profile's page load needs to see. Falls back to `DEFAULT_PROFILES` (`two_of_us`/`loose_ends`) if empty, so existing bookmarks keep working untouched. `renderProfileSelect()` rebuilds the dropdown's `<option>`s from it on every `boot()` (plus a trailing `✎ Edit profiles…` entry) — if the URL's `?profile=` isn't in the registry (a hand-typed one-off), it's shown unpersisted rather than left blank. Picking `__manage__` is intercepted in `switchProfile()` before the normal navigation and opens `#profiles-modal` (`openProfilesModal()`) instead, where `addProfile()` slugifies the typed name into an id (de-duped against collisions) and `deleteProfile()` removes the registry entry plus that profile's `rep_v2_<id>`/`rep_github_config_<id>` localStorage — a confirm() first, and it only ever touches local data, never the repo's `repertoire_<id>.json`. A brand-new profile just starts with the default empty `db` (no seed file to fetch yet) until its first ⬆ Push creates one.
- **Header height is dynamic, not hardcoded**: the header wraps to a different number of rows depending on screen width (and whether the mobile ⋯ panel is open), so everything sticky-positioned below it (`#sync-banner`, `.sets-sidebar`, `.set-detail-header`) reads the `--hdr-h` CSS var instead of a fixed px offset. `syncHeaderHeight()` measures the real `<header>` and writes the var — called from `boot()` (plus once more after `document.fonts.ready`, since the async Google Fonts swap can nudge wrap height), from the debounced `resize` listener, and from `toggleHdrMore()`. Forgetting to call it after something that changes header content/height is exactly the bug this replaced — content used to disappear behind the sticky header on any screen where the header ran taller than the guessed 58px/76px.
- **Mobile header (≤600px)**: the tune toggles, UG link, Export, and Import fold behind a `⋯` button (`#hdr-more-toggle` / `toggleHdrMore()`) into `#hdr-more`, which is `display:contents` above the breakpoint (so it's invisible as a wrapper — those items sit inline in `.hdr-actions` exactly as before) and a full-width dropdown panel below it. Title/profile/⋯+Refresh+Pull+Push stay on the primary row; the tab nav gets `order` bumped onto its own full-width row underneath.

## Files

| File | Description |
|------|-------------|
| `index.html` | Entire app — HTML, CSS, JavaScript in one file |
| `repertoire_two_of_us.json` | Seed data for the default (`two_of_us`) profile — the one actually loaded day to day |

## Data Format

```json
{
  "songs": [
    {
      "id": "unique-id",
      "title": "Song Title",
      "tags": "Neil Young, rock, acoustic",
      "key": "G",
      "capo": "2",
      "harp": "G",
      "ugLink": "https://tabs.ultimate-guitar.com/...",
      "crd": "Am        C          G\nLyric line one...",
      "tryOut": false
    }
  ],
  "setlists": [
    {
      "id": "unique-id",
      "name": "Setlist Name",
      "type": "live",
      "date": "2026-08-07",
      "items": [
        { "type": "section", "name": "Set 1", "collapsed": false },
        { "type": "song", "songId": "id1" },
        { "type": "section-end" },
        { "type": "song", "songId": "id2", "altSongId": "id5", "useAlt": false },
        { "type": "section", "name": "Encore", "collapsed": true },
        { "type": "song", "songId": "id3" }
      ]
    }
  ],
  "tuneUp": false
}
```

- `tuneUp` (top-level, global): tracks whether the "Half-step down tuning" header toggle is currently on. Flipping it bumps (or restores) every song's `capo` field by 1 fret across the whole library (a confirmed bulk edit, `toggleGlobalTune`); the CRD reader's own Capo readout folds that bump back in on top of the root/playing-key distance (`computeCapo`).
- `setlist.type` is `'live'` (a real gig, has a `date`) or `'generic'` (a working/rehearsal list, no date). Drives the left-pane split — see "Setlists" below.

- `song.tryOut` (boolean, default off): a checkbox on the song itself, settable from the Songs tab row (`toggleSongTryOut`), its add/edit modal, its inline edit row, or a setlist row's ✎ edit. Marks it as out of the repertoire for now — the Songs tab's repertoire-scope filter reads it (`songsScopeFilter`, see below); there's no dedicated setlist or view built on top of it beyond that.

- `song` items resolve to `altSongId` instead of `songId` when `useAlt` is true — lets a slot's live song be swapped without reordering.
- `section` items are collapsible chapter headings that live inline in the same flat `items` array — every `song` item after one belongs to it by position (not by any nested/reference structure) up to the next boundary: another `section`, an explicit `section-end`, or the end of the list. `collapsed` just controls whether those rows are rendered; it never changes what plays, prints, or counts.
- `section-end` items are an invisible boundary marker with no other fields — they close a section early instead of letting it run to the next header. See "Sections" below.
- Legacy setlists with a flat `songIds: [id, ...]` array are migrated to `items` on load (`migrateSetlists()`), which also silently drops any leftover `subset` items from the retired embed-another-setlist feature (replaced by `section`). The same pass backfills a missing `setlist.type` — `'generic'` by default, except a handful of known pre-existing gigs matched by name (`LEGACY_LIVE_DATES`) that get `'live'` plus their date, so setlists saved before the live/generic split still land in the right list.

## Key Implementation Details

- **Theme**: Deep blue-black / muted teal (`#3d9e8c`) studio/DAW aesthetic
- **Song title links**: `songTitleLink(s, opts)` is the one shared fallback chain — CRD reader link (if `s.crd`) → Ultimate Guitar link (if `s.ugLink`) → plain text — used everywhere a title appears (Songs table, setlist rows, Play mode). `opts` covers each call site's own markup: `cls`, `plainTag` (wrap the plain-text fallback too, or leave it bare), `wrap` (additionally wrap the title text itself, e.g. `'strong'`), `crdStop` (stopPropagation before opening the reader), `ugOnclick` (raw onclick for the UG link, e.g. stopPropagation or Play mode's `playOpenedUG` flag). The visualizer's bubble-detail pills (`showDetail`) build their own markup instead — there the whole pill is the link, with badges alongside the title inside it, not just the title text, so it didn't fit the same shape.
- **Visualizer**: Animated glass bubbles packed with a circle-packing algorithm, grouped by tag; bubble size proportional to song count. Radius range (`BUBBLE_MIN_R`/`BUBBLE_ADD_R` in `renderBubbles()`) raises its floor on screens under 600px wide so the smallest bubbles still have room for their label instead of crushing it against the glass edge — same ceiling either way
- **Songs table**: Inline editing (click row or ✎ button); sortable columns; tag autocomplete dropdown on tags fields; toolbar has two independent dropdowns — chord sheet (`songsCrdFilter`: Any chords/🎸 Has chords/No chords, `setSongsCrdFilter`) and repertoire scope (`songsScopeFilter`: Any song/In repertoire/🧪 Try out, `setSongsScopeFilter` — "In repertoire" means NOT `tryOut`) — alongside the text search; all three apply together (AND) in `renderSongs()`. Both reuse the header's `.profile-select` dropdown styling rather than introducing new CSS. Each row's actions cell also carries a live `tryOut` checkbox (`toggleSongTryOut`) — same field as the modal/inline-edit checkbox, just a one-click path to it that doesn't require opening edit mode; `event.stopPropagation()` on its wrapping `<label>` keeps the click off `handleRowClick`'s "open inline edit" fallback
- **Quick UG Import**: Parses title and artist from a UG URL slug — no network request needed. Pattern: `/tab/{artist}/{title}-{type}-{id}`
- **Ultimate Guitar links**: Normalized to `tabs.ultimate-guitar.com` Universal Link domain for iOS app compatibility
- **CRD reader**: A song can carry a `crd` field — a plain-text chord/lyric sheet, entered manually (Add Song modal, inline edit, or the full-page editor). When a song has `crd`, its title everywhere (songs table, setlists, play mode, visualizer pills) opens the in-app CRD reader (`openCrdReader`) instead of the UG link. Because it's an in-page overlay rather than a navigation, it also sidesteps the AirTurn/UG Universal-Link app-switch issue during Play mode.
  - **Full-screen overlay** (`#crd-reader`), not a small modal. The header/toolbar (`.crd-chrome`) is tap-to-toggle — tapping the sheet hides it for more reading room, tapping again brings back the "← Back" button and controls.
  - **Chord detection**: recognizes chords either inline as `[G]` (ChordPro-style) or on their own "chord line" above the lyrics, including slash/bass chords (`G/D`, tolerant of spaces `G / D` and parens), augmented (`aug`/`+`), and bar/repeat notation (`|`, `%`, `N.C.`) without breaking detection of the real chords on that line. `[Verse]`/`[Chorus]`/etc. in brackets render as section labels, not chords.
  - **Root key vs. Playing key**: `s.crd` is always stored written in the song's `key` (root). The reader header shows two editable note-name inputs — **Key** (`crd-key-input` → `crdEditKey`, the root) and **Playing key** (`crd-tkey-input` → `crdEditTKey`, the shape actually being played) — plus a read-only **Capo** badge computed from the two: `capo = (semitone(root) − semitone(playingKey) + 12) % 12 + (tuneUp ? 1 : 0)` (`computeCapo`). Opening the reader defaults Playing key to whatever's implied by the song's saved `key`/`capo`/tuning (`deriveDefaultTKey`) — the equivalent of the old auto-capo baseline, just expressed as a note name.
  - Key/Playing-key inputs accept a root note plus an optional quality restricted to `KEY_QUALS` (`''` major, `m` minor, `mmaj7` minor-major-7) — nothing else (`parseKeyName`/`formatKeyName`; e.g. `Am`, `F#`, `Gmmaj7` parse, `Am7`/`Csus4` don't). Only the pitch matters for the capo/transpose math, but `deriveDefaultTKey` and the −/+ steppers carry the quality through unchanged so e.g. an `Am` song defaults to (and steps between) minor playing keys, not major.
  - Editing **Playing key** (−/+ semitone steppers `crdTKeyStep`, ↺ `crdTKeyReset` back to the saved default, or typing directly) live re-transposes the on-screen chords (`crdChordsEff`, computed against the song's *actual saved* key, not any pending root edit) and updates the Capo badge. Editing **Key** (the root) only updates the Capo badge/preview — it never touches the displayed chords or the saved sheet until committed.
  - **Committing** (`crdCommit`, bound to `#crd-store-btn`): label/behavior depend on what's dirty. If only the resulting capo differs from what's saved, it reads **"Save capo"** and just writes the new `s.capo`. If the root key was edited, it reads **"Update root"** and additionally shifts `s.crd` by the exact semitone interval between the old and new root (`transposeCrdText`) and writes the new `s.key` — i.e. reloading without committing always reverts to the last-saved root. `crdUpdateStoreBtn()` keeps the label/enabled state in sync on every keystroke via the lightweight `crdMetaEdited` (which deliberately avoids rebuilding `#crd-meta`, to not steal focus mid-typing).
  - **Half-step tuning and the reader**: `tuneUp` bumping every song's stored `capo` (via `toggleGlobalTune`) never changes which chord shapes are shown — those come purely from root-vs-playing-key — only the Capo badge, which folds the tuning bump back in via `computeCapo`.
  - **Keyboard Mode**: `keyboardMode` is a device-local display preference (`localStorage['rep_keyboard_mode']`, header checkbox `keyboard-mode-toggle`/`toggleKeyboardMode`) — not part of `db`, so it isn't JSON-persisted or pushed/pulled with the data. It relabels every "Capo N" as "Transpose ±N" wherever a capo value is shown (song badges via `kchBadges`, the CRD reader's badge, print sheets, the Add Song modal's field label, both inline-edit placeholders, and the "Save capo"/"Update root" commit button/confirms) via `capoWord()`/`capoText()`/`capoBadgeText()`/`capoWrap()`. The stored `s.capo` fret count never changes — only fret counts over 6 are *displayed* wrapped an octave down as the equivalent negative shift (capo 7 → Transpose -5 … capo 11 → Transpose -1), since that's the shift a keyboard player would actually play.
  - No delete button in the reader — deleting a song only happens from the Songs tab, so it's never one misplaced tap away while reading/playing.
  - **Full-page editor** (`#crd-editor`, `openCrdEditor`/`closeCrdEditor`): the "⤢ Full editor" button next to the CRD field (Add Song modal `f-crd`, Songs table inline edit `ie-crd`, or setlist inline edit `sl-ie-crd`) pops a full-screen editor — a single full-width raw textarea by default, with a "👁 Preview" header button (`toggleCrdEditorPreview`/`setCrdEditorPreviewing`) that swaps it for a live-rendered preview (same `renderCrdHTML` the reader uses, always at transpose 0 — no playing-key/capo math here), one full pane at a time rather than a permanent side-by-side split; the preview is only (re-)rendered at the moment you switch to it. It also carries just the root **Key** field (`crdEditorKey`), no Playing key/Capo — it works even for a not-yet-saved song (no `db.songs` entry to read) by deriving the sibling Key field id straight from `targetId` (`"f-crd"` → `"f-key"`, `"ie-crd"` → `"ie-key"`, etc.). On "← Done", the crd text *and* Key sync back into those sibling fields (`dispatchEvent('input')`, so the outer form/Save picks them up). Doubles as the fix for a sheet transcribed in the wrong key — edit the raw chords directly and update Key alongside them; no separate "re-root" tool needed (there used to be one in the reader itself, removed once this covered the same case).
  - **Keyboard**: Up/Down/PageUp/PageDown scroll the sheet, Escape closes the reader (ignored while typing in a text field).
  - No chord/fretboard diagrams — removed after trying a diagrams-strip and a tap-to-popup version; the reader is text-only now.
- **Setlists**: Reordering via pointer-events drag, grabbing a row's ⠿ handle (`initDrag`/`startSlDrag`/`onSlDragMove`/`endSlDrag`/`cleanupSlDrag`, driven by the module-level `slDrag` state) rather than the HTML5 drag-and-drop API — `dragstart`/`dragover`/`drop` never fire from touch input on iPad Safari, this app's actual platform, so native DnD silently did nothing when grabbed on-device even though it worked with a mouse. Pointer Events fire uniformly for mouse/touch/pen. Touch-friendly ↑↓ buttons (`moveSlSong`) remain alongside it. Both share `slBlockLen`/`sectionBlockEnd`/`moveBlockTo`: dragging or ↑/↓-ing a section header always carries its whole block — the header, its songs, and the `section-end` that closes it, if any — rather than just relocating the header and stranding its songs at the old spot. Dragging a lone song onto a section header's lower half drops it inside as the section's first song if that section is expanded, or right after the whole section if collapsed (a collapsed section has nowhere to visually show an "inside" landing spot); dragging a song past the end of any section — its own, or one it's being dragged into — always lands it right after that section, never orphaned mid-block. `selectedItemIdx` is kept pointing at the same logical item across any of this via `reindexSelection`, which tracks the item by object reference rather than re-deriving index arithmetic after a multi-item block move.
  - **`moveSlSong` internals** (↑/↓ buttons): dispatches on direction and on whether `idx` is a lone song (`len===1`, via `slBlockLen`) or a whole section header (`len>1`), down to a shared `doMove`/`exitSectionInPlace` tail. Up is always a plain adjacent single-slot swap for a section header — whatever sits right before it can never have more of its own content trailing behind, since a section always auto-closes at the next header regardless (see the `section-end` note below), so there's nothing to strand. Down for a section header isn't: if what immediately follows is itself *another* section's header, a naive single-slot swap would leapfrog just that header and strand its songs behind with no header of their own — silently losing them out of any section (collapsed just hides the wreckage, it isn't the cause). Fixed by swapping past the neighbor's own full extent (`slBlockLen` at the far side) rather than assuming a lone item. `onSlDragMove` has the matching case for drag: dropping a *dragged section* onto another section header's lower half always lands after that neighbor's whole block, never wedged between its header and its songs.
  - **A plain song's ↑/↓ near a section boundary** is its own set of cases, since unlike a header it can be swallowed by what it's stepping into rather than what it's stepping past:
    - Stepping down or up across the boundary of a *collapsed* section (its header going down, or the `section-end` closing it going up — `collapsedBefore`/`sectionStartFor` replay `renderSetDetail`'s own collapsed-state walk standalone to check) would tuck the song inside as a newly-hidden row, its own ↑/↓ buttons vanishing with no warning. Skipped over the whole block instead, landing on the far side, so a button-stepped song always stays visible.
    - Stepping down off the end of a nested song with nothing further in its own section to swap against — either because it's the last thing in a *trailing* section (open-ended, no `section-end` to ever cross) or because a *different* section's header sits immediately next (two sections back to back, nothing separating them) — used to either no-op or, worse, swap straight into the next section in one step, skipping the "between the two sections" position a single ↓ press implies. `exitSectionInPlace` fixes both the same way: insert a fresh `section-end` right before the song instead of moving it — a pure membership change (it stops being nested, loses its `sl-nested` indent, confirmed via toast since nothing visibly shifts) rather than a reorder, leaving a second ↓ press to actually enter whatever comes next.
    - Approaching a section from *outside* (not currently nested in anything) is the one case that's still a single step: enters as the section's first song if expanded, or skips the whole block if collapsed (can't show an "inside" landing spot while collapsed) — same rule drag-and-drop uses for a dropped lone song.
  - **Live vs. Generic**: the left pane (`renderSets`) splits `db.setlists` into two groups by `sl.type` — **Live** (`type:'live'`, has a `date`), sorted soonest-first (`formatSetDate` renders it e.g. "7 Aug 2026"), and **Generic** (anything else), sorted alphabetically. The setlist modal's "Live (has a gig date)" checkbox (`toggleSetLiveField`) reveals/hides the date input; marking a setlist Live without a date is rejected (`saveSetlist`). Un-checking it on an existing setlist drops `sl.date` entirely, so it falls back to the alphabetical Generic list with nothing stale left behind.
  - **Inline song editing from a setlist row**: the ✎ button on a `slRow` opens the exact same fields as the Songs tab's inline edit (title/Key/Capo/Harp/Artists/UG link/CRD) — it edits the underlying song, not anything setlist-specific. Tracked via a separate `slEditSongId` (not `inlineEditId`), with its own `sl-ie-*` input ids and `slEditRow`/`startSlEdit`/`saveSlEdit`/`cancelSlEdit`, so it can never collide on DOM ids with the Songs tab's `songEditRow`/`inlineEditId` if the same song is (at least technically) in an editing state in both places at once.
  - **Row numbering** (`sl-num`): counts songs only, never section headers — `renderSetDetail` tracks a separate running `songNum` alongside the raw `items[]` index `i` (which everything *else* on the row — `data-idx`, `selectItem`, `moveSlSong`, `removeSlItem` — still uses, since those genuinely need the real array position). `songNum` still increments for a song hidden by collapse or `slCrdFilter`, so the number stays a stable "song N of the whole setlist" regardless of what the view narrows away, rather than shifting as sections/filters come and go.
  - **Setlist detail chord filter** (`slCrdFilter`, toolbar dropdown `setSlCrdFilter` — same three options/styling as the Songs tab's `songsCrdFilter`): narrows which rows `renderSetDetail` shows by whether the resolved song has `crd`. Purely a view filter, like the Songs tab's — it never touches `sl.items` — implemented the same way a collapsed section hides its rows, so a filtered-out song is just skipped during the render pass rather than removed from the data.
  - **🧪 Try out highlighting**: a setlist row for a `tryOut` song gets a `sl-tryout` class tinting the whole row (on top of the small "🧪 Try out" chip `kchBadges` already adds to every view) — easy to miss a stray try-out song scanning a long setlist otherwise, since the chip sits among the Key/Capo/Harp badges.
  - **Add Songs / Set Alternate pickers** (`openAddSongsModal`/`renderPickList` and `openAltModal`/`renderAltPickList` — same layout and behavior, since choosing an alternate is the same "find a song" task as adding one): two checkboxes narrow the picker beyond a plain song search, both reset on every open. "Hide songs already in this setlist" (`*-hide-existing`, checked by default — the original, only behavior) filters out songs already in `sl.items`, via `setlistSongIds(sl)` — a `Set` of every slot's `songId` *and* any `altSongId` set on it, since an alternate is just as "in this setlist" as the song it stands in for. Unchecking the box just reveals an already-used song marked "✓ In setlist" rather than hiding it — it's still fully selectable/pickable, never `disabled`, since a song can legitimately go into a setlist twice (a reprise) or double as an alternate elsewhere. "Hide 🧪 Try outs" (`*-hide-tryout`, unchecked by default) is an independent optional narrowing; songs shown either way carry the same "🧪 Try out" chip as elsewhere. The alt picker additionally always excludes the slot's own current song outright (can't be its own alternate — the one hard exclusion) and always exempts its *current* alt from the "already in setlist" hint, pre-selecting that radio, so reopening to change an existing alternate still shows it picked.
- **Alternate songs**: A song slot can carry an `altSongId`; the ⇄ button flips which one (`useAlt`) is live, for last-minute swaps without reordering
- **Sections**: A setlist can carry `type:'section'` header items to group its songs into collapsible chapters (Set 1, Encore, …) — purely a display grouping over the same flat `items` array, not a separate structure. A section runs open-ended — everything after it belongs to it — until the next boundary: another `section` header, an explicit `type:'section-end'` marker, or the end of the list. `section-end` is purely structural: it renders nothing (`renderSetDetail`'s grouping loop just resets `nested`/`collapsed` on hitting one) and only exists to let a section close *before* the next header, instead of running on to it. Collapsing a section (`collapsed`) just hides the song rows under it; it never affects `resolvePlayableSongs()`, which is a plain `map`+`filter` over all items (section/section-end items resolve to no song via `resolveItemSong` and are skipped automatically). New songs are inserted right after whichever row is currently selected (`selectedItemIdx`), so selecting a row inside (or the header of) a section adds to that section. New sections (`saveSection`) are inserted right after the selection too, but a real song immediately following the insertion point (i.e. not already another boundary) gets an auto-inserted `section-end` spliced in right after the new header — so it starts empty and that song stays exactly where it was — matching how a real chapter break works: open-ended is fine for a trailing section like "Encore" with nothing after it, but a section inserted mid-list needs an explicit end so it doesn't swallow what was already there. No UI removes a `section-end` directly (there's no visible row for one) — deleting the section header that precedes one just leaves it in place as an inert boundary, which is harmless since it isn't reachable/owned by anything else.
- **Play mode**: Scroll-snap drum-roll UX — fixed 100px items, CSS `scroll-snap-type: y mandatory`, centered item detected via `scrollend` + debounced `scroll`. Auto-advances on return from UG via `visibilitychange`. `getPlayEntries()` is the flat per-slot list driving it — like `resolvePlayableSongs()` (every song, section or not, collapsed or not), but each entry also carries the section it's nested under (if any) and its *inactive* alternate (if the slot has one), plus the item's real `sl.items` index; `getPlaySongs()` is just `.map(e => e.song)` over it for callers that only need the song list. A nested song's section name shows as a `[Name]` tag — inline (in accent teal, bold — visible at a glance across the dim, low-opacity non-current rows) before the title on a non-current row, same single line so it can't break the fixed-height scroll-snap math `PLAY_ITEM_H` depends on; on the expanded current row it's instead its own standalone accent-colored pill badge above the title, since that row isn't height-constrained the same way (its badges/alt already routinely render past the box, same as before). An alt, if the slot has one, only ever shows on the *current* row — a full accent-pill button (`alt: Title`, ⇄ icon), the whole pill clickable (not just a small icon) via `togglePlayAlt` (the same effect as a setlist row's ⇄/`toggleAltUse` but keyed off `playSetId` rather than `activeSetId`) so a last-minute swap doesn't require leaving the performance view or hunting for a small tap target.
- **Print** (`openPrintModal`/`doPrint`): a setlist prints with every section fully expanded and its songs indented under a heading row, regardless of on-screen collapsed state — collapsing is a screen-space convenience, not something that should hide songs from a physical sheet — with song-only sequential numbering (no jump for section headers, same principle as `sl-num` below). A slot's *inactive* alternate, if it has one, prints as a small italic "alt: Title" line under the active song — same info Play mode shows, so a paper copy still tells you a swap is available. Printed via `window.open('', '_blank')` + `document.write()`/`close()` + `print()`, same mechanism the app has always used — a hidden `<iframe>` was tried instead (to solve the "no way back" problem below without a second window), but WebKit doesn't reliably scope `print()` to just an iframe's own content, so the print preview could come out blank. Standalone "Add to Home Screen" iPad Safari has no browser chrome at all — no tabs, no back button — so this second window would otherwise be a dead end once the print sheet (or its Cancel) closes; solved with an explicit in-page "← Close" button (`window.close()`, which works because the window was opened by this script), hidden from the actual printed output via `@media print`.
- **GitHub push**: Uses GitHub Contents API (PUT) to commit `repertoire.json` directly; config stored in `localStorage`
- **Repo sync**: On boot, fetches `repertoire.json` and compares fingerprints; shows banner if remote differs
- **Force refresh**: The header's "🔄 Refresh" button (`forceRefresh`) is a manual, always-overwrites version of the same idea — refetches `SEED_FILE` (cache-busted) right now and loads it unconditionally after a confirm, no GitHub token needed (unlike ⬆/⬇ Push/Pull, which go through the authenticated Contents API and so always see the exact latest commit even if GitHub Pages' CDN hasn't caught up yet). It doesn't stop at the data — after saving the fresh JSON to `localStorage` it calls `hardReloadPage()`, which appends a `_hr=<timestamp>` cache-bust param and `location.replace()`s to it, forcing a real network refetch of `index.html` itself (everything — HTML/CSS/JS — lives in that one file, so a stale cached copy would otherwise keep serving old app code even with fresh data). `boot()` strips `_hr` back off the visible URL via `history.replaceState` on the way back in. Plain `location.reload()` isn't reliable enough for this, particularly in iPad Safari's "Add to Home Screen" standalone mode, which is more aggressive about caching and has no visible reload button at all.
- **Viewport fix**: Resets viewport meta on `visibilitychange` to prevent iPad Safari zoom-out on app resume
