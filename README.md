# Repertoire

A single-page web app for managing a musical repertoire — built to run on an iPad via GitHub Pages, with no backend or build step required. Export and Import live behind the header's `⋯` button. Also usable on a phone: under 600px wide, the header folds all its less-used controls behind `⋯`.

## Features

### Songs
- Sortable, searchable table of all songs — the first tab the app opens on (the old tag-bubble Visualizer tab was removed)
- **Sort by artist** — a song's artist is its first tag. Tap the **Artist · Tags** column header to sort by artist (then title), songs with no artist last
- Two filter dropdowns, alongside the text search: chord sheet (Any chords / **Has chords** / **No chords**) and repertoire scope (Any song / **In repertoire** / **❓ Not ready**)
- Check a song **❓ Not ready** right from its row — no need to type a tag — and it's excluded from "In repertoire" above until you uncheck it again
- Check **🎤 Lyrics only** (row, Add Song or edit) and the chord reader shows just the lyrics and section labels — the chords stay in the sheet, untouched
- Add, inline-edit, and delete songs
- Each song stores: Title, Tags, Key, Capo, Harp, Ultimate Guitar link
- Key / Capo / Harp shown as badge chips in all views
- **📋 Paste UG** (header, next to ● Start live) — in the UG app tap Share → Copy link, then 📋 Paste UG: the import dialog opens with title and artist filled in when the link or share text has them (the UG app's short `/tab/<number>` links don't, so type them in the editable Title and Tags fields); copy the chords in the UG app and tap **📋 Paste chords**; set Key (root), Capo and Not ready right there, and **Add Song** saves it in one step
- **📋 Paste chords** — copy the chords in the UG app (Official tabs too), then tap **📋 Paste chords** in the UG import dialog or **📋 Paste** next to the Chord Sheet box in Add Song and inline edit; UG's markup and stray spacing are tidied. Copying a UG link (Share → Copy link) and tapping 📋 Paste fills the song's UG link instead
- **CRD reader** — paste in your own chord/lyric sheet per song (inline `[G]` chords or a chord line above the lyrics, `[Verse]`/`[Chorus]` section labels; any chord spelling is recognised — `7sus4`, `m7b5`, `maj9`, `add9`, `7M`, `G7(b9)`, slash bass `D/F#` and so on — and transposes cleanly); if present, the title opens it in a full-screen in-app reader instead of Ultimate Guitar, with a UG link and edit still one tap away (no delete here — that's Songs-tab-only, so it's never a stray tap away mid-reading)
  - **Tap a chord for its diagram** — a small popover shows how to play the chord as displayed: guitar fretboard normally, piano keyboard in Keyboard Mode, plus its notes. Tap anywhere (or Escape) to close; it doesn't affect auto-scroll or the pedal
  - **Chords as played** — the sheet is stored in the shapes you play. The header shows the **Key** (root), the **Playing key** and the **Capo** that links them (root = playing key + capo, −1 with half-step down tuning). Change the Playing key to transpose the sheet into other shapes (the capo follows, the root stays), or the Key to change the root (the sheet stays, the capo follows). Nothing's saved until you tap **💾 Save** — reload without it and it's exactly as it was
  - Opens in the song's saved playing key, showing the sheet exactly as stored
  - Tap-to-hide header for a distraction-free view; keyboard scrolling (arrow keys / Page Up/Down), with a **Scroll %** control for how far each press jumps
  - **Pedal Auto-scroll** — a header toggle (device-local) for a foot pedal that sends Up/Down keys. When on, the reader gets an **Auto** play/pause button (it keeps the same look either way, so the toolbar never shifts; the status pill bottom-right shows whether it is playing) with a speed level in steps of 5 (15 ≈ a full sheet in 3½ minutes), opening a song doesn't start scrolling until you tap play (sheet, Space or pedal), tapping the sheet or Space plays/pauses, and a status pill bottom-right shows/hides the toolbar. On the pedal: by default a single short tap plays/pauses (Play resumes from where it paused) and a quick double press on Down speeds auto-scroll up and on Up slows it down by a step of 5, e.g. 15 → 20 → 25 (the new speed shows in the status pill; the toolbar −/+ also step by 5); a button at the top of the Live tab, labelled **Tap play** or **Tap speed** after the current choice, swaps them (tap = speed, double press = play/pause); it's one setting for the whole app on that device, not per song. A tap acts about half a second after you let go, so a double press or a hold never triggers it; and holding a side scrolls the sheet down/up like the arrow keys (auto-scroll pauses meanwhile and carries on from there). Each song remembers its own speed automatically: whatever you last set while it was open is used next time (and syncs with Push/Pull); songs you haven't adjusted start at 20. Holds are told apart from double presses by timing, and recognised even on pedals that send a fast stream of repeated presses instead of a true held key. Touching the sheet pauses auto-scroll briefly, then it carries on. Off, the reader works exactly as before
  - **⤢ Full editor** — a full-screen, full-width view for comfortable long-sheet editing, with a **👁 Preview** button to swap in a live rendering (styled chords, section labels — the same look as the reader) when you want to check it. Just a Key field alongside it (no Playing key/Capo here) — it saves straight into the song when you tap Done, and it works even before the song's been saved. Also the go-to for fixing a sheet transcribed in the wrong key — edit the chords and Key together, right there
- Tag autocomplete when editing — suggests existing tags as you type

### Setlists
- Create and manage multiple setlists
- **🖼 Setlist image** — any setlist can have a small picture (✎ → Image: a poster, a venue photo…), shown as a thumbnail in the list and the setlist header; live setlists also get a **Place**
- **⬆ Upload** (gig setlists) — puts the gig on the audience page's **past gigs** list: its songs, date, place and image (asks first; uploading the same date again replaces it, keeping its likes and comments). If you took a 📸 snapshot that night, its likes come along, so the hearts from the gig itself are kept
- **⧉ Duplicate** a setlist — copies everything (sections, alternates, date) as "<name> (copy)"
- **Setlist groups** — the left pane lists setlists in three collapsible groups: **Generic** (working lists, alphabetical), **Live** (gigs) and **Rehearsal**, the dated ones most recent first (shown e.g. "Rehearsal · 7 Aug 2026"). A soundcheck is nested under the gig on the same date (tap `▾ 1 SC` on the gig to hide/show it); with no gig that day it's listed in Live on its own. Which groups are open is remembered on the device. Mark a setlist Live and pick its type and date from the same modal you name it in; older live setlists count as gigs
- **● Start live** — a header button that asks whether it's a gig, rehearsal or soundcheck, then notes down every song you open in the chord reader, in order (re-opening the song you just played isn't counted twice). A red **LIVE** pill shows the count (hidden while the chord reader is open), and recording carries on if you close the app. **■ Stop** saves the songs as a live setlist of that type, dated today, and pushes it
- Two-column layout: setlist selector on the left, song list on the right
- **⎙ Print** a setlist (or the whole song list) — sections expanded, optional capo/harp column. In the home-screen app (where iOS ignores printing) it makes a PDF and opens the share sheet, which has **Print** and Save to Files; in a browser tab it opens the printer menu directly
- Add songs, remove songs, reorder by drag-and-drop or ↑↓ buttons
- **# Go to position** — the # button next to ↑↓ asks for a position number (the box starts empty, the current position is shown above it) and moves the song straight there
- **+ Add all songs** or **+ Add artist** (pick an artist or tag) in the Add Songs window, to fill a big setlist in one go. Songs already in the setlist are skipped, and ticking "Hide Not ready songs" leaves not-readts out too
- **✎ Edit right from the row** — same full edit form as the Songs tab (Title, Key, Capo, Harp, Artists, UG link, CRD), just without leaving the setlist
- **Alternate songs** — give any song slot a backup; swap which one is live with one tap
- **Sections** — collapsible chapter headings within a setlist (e.g. "Set 1", "Encore"); add songs directly under a section, collapse it to a single row, expand/collapse all with one tap. Adding a section always starts it empty — songs already after your selection stay right where they were, they don't get swallowed into the new section
- **Play mode** (▶ Play in the **Live** tab, for the setlist picked there; it works without any Firebase setup) — scroll-snap drum-roll view (like iOS date picker): current song centered and large, others dimmed; auto-advances when returning from Ultimate Guitar

### Live (audience requests)
- A **Live** tab for taking song requests from the audience at a gig. Pick one setlist (e.g. the big list of everything you might play) and **📣 Publish to audience**. Your audience scans a QR code (shown at the top left of the tab; **⤢ Show big** prints it as an A4 poster in Italian — "Richiedi una canzone!" — with "Filmaci e taggaci!" and your Instagram handle). The audience page also shows a **Filmaci e taggaci!** card linking to your Instagram (@twoofus_7478 for Two of Us) and gets a phone page in Italian, `request.html`, showing that setlist as big, easy-to-read tag bubbles (on a phone, compact colourful tag chips), with a search box to find a song directly. They tap a bubble, then a song, add an optional name and message, and send. **Something else?** lets them ask for any song as free text. No app or account is needed on their side
- Next to Publish, choose what the audience page shows: **tags** (bubbles, or chips on a phone) or **all titles**, every song in a random order. That's only the default: people can switch between the two with a small switch on their phone. The titles list reshuffles every 15 minutes (never while someone is scrolling it). On the phone page the Instagram card and "Chiedi un’altra canzone o scrivici qualcosa" come first and the search box is at the bottom. Changing it while published updates the page straight away
- **🎤 Gig** — at the top of the Live tab's left column, type the gig's place and pick its date and start time. They show at the top of the audience page ("Si comincia sabato 29 novembre alle 21:30 · 📍 place" before the start, then just the date and time), so people who scan the QR before the show know where and when. Saved on the iPad per profile, sent with Publish, and updated straight away when changed while published; clear both fields to hide the card. **🖼 Add image** next to them uploads a picture (e.g. the gig poster, any photo the iPad can open): it's shrunk to a JPEG of at most 1200 px and shown as a small picture in the gig card at the top of the audience page, in place of the 🎤, next to the time and place; ✕ removes it. It needs the `poster` rule from FIREBASE_SETUP.md (paste the rules again if you set Firebase up before)
- What the audience can pick from is the chosen setlist **plus every song not marked ❓ Not ready**, so they can ask for anything you're able to play. The Live tab's setlist column shows each song's key, capo, harp and other badges, like the Setlists tab, with a narrower requests column on the left
- Requests have their own **Requests** tab (next to Live): they pop up there in real time, with a chime, a toast and a red count on the Requests tab button (whatever tab is open). The tab's top bar has the **Requests open** switch (only on this tab), an **Oldest first / Newest first** sort by the time each request was sent (remembered on the iPad), and **Clear requests**. Opening or closing requests is just a switch: it never asks, saves or clears anything.  Each shows when it was sent (date and time), the requester's name (or "Anonymous", since the name is optional) and a location check: **📍 In the audience**, **⚠ Not in the audience · 249 km**, or **📍 No location** if their phone didn't share it. "In the audience" means within 300 m of the venue (plus whatever margin the phones' GPS accuracy needs). The venue is where the iPad was when you tapped **● Start live** (or first published); **Set here** in the Live tab sets it again at any time, without unpublishing or clearing requests, and every request's badge (old ones too) is rechecked against the new spot. The venue location stays on the iPad. The audience page remembers each person's name for next time Every pending request has a **✓ Played** button (for a song request it marks the song played, settling all its requests); a song's ✓ in the Live tab's setlist column does the same (songs outside the setlist that were requested, liked or played appear below it, under "Requested, liked or played, not in this setlist"). **✕** dismisses a request; dismissed and played requests fold into a "done" list, shown by default (Hide/Show done toggles it), with **↺** to undo. **🗑** deletes a request for good (after a confirm), from the iPad and from Firebase
- In the audience page's song lists, each song carries a small note when it has been requested (with the count) or already played; there's no board at the top. Names, messages and free-text requests are only ever shown to you. "Chiedi un’altra canzone o scrivici qualcosa" lets people type either a song that isn't in the list or just a comment for the band (up to 200 characters); it shows in Requests as 💬 — ✓ Played if it was a song, ✕ once you've read a comment. Tap ✓ next to a song in the Live tab's setlist to mark it played. Closing the chord reader on a published song marks it played automatically (tap its ✓ again to undo)
- **Requests open** switch to pause and resume intake, **Unpublish** to take the page down, **Clear requests** before each gig (each phone also checks its own requests every 30 seconds, so its "L'hai chiesta tu" marks go away once you clear or 🗑 delete them). The QR code and **Copy link** use a short link: `tinyurl.com/4cys25ft` for Two of Us, otherwise `…/Repertoire/r/?<project>`, both redirecting to the full one. Each profile's audience link never changes, so a printed QR code keeps working
- The Live tab's top bar groups its buttons by function: **Play** (setlist, ▶ Play, pedal mode), **Audience page** (what it shows, Publish/Update, Unpublish, connection status), **Archive** (📸 Snapshot live, 🗂 Show past), and Sign out on its own. The **▾** button at its start collapses the bar to a single **▸ Controls** button (remembered on the iPad)
- The Live tab's left column is a stack of collapsible boxes: **🎤 Gig & venue** (place, time, image and the venue location), **📱 Audience page** (QR code and visits), **🎶 Now playing**, and **❤ Likes** (closed by default). The iPad remembers which ones you left open
- **🎶 Now playing** — shown by default (**▶ Start** brings it back after a Stop): at the top of the audience page it shows the song you have open in the chord reader ("Ora suoniamo") and the two before it, three songs at most; when you close the reader the song moves down with the earlier ones. **■ Stop** hides it from the audience page, **Clear** (after a confirm) forgets them, together with the full history of every song opened, which 📸 Snapshot live saves. Updated straight away while published (phones see it within 15 seconds)
- **📸 Snapshot live** — a button in the Live tab's top bar (Archive group) saves the audience page (setlist name, gig, the full Now playing history with times, visit numbers), every request and the like counts to the repo's `data` branch as `live_snapshots/<profile>/<date_time>.json`, using the ⬆ Push GitHub settings; without them, or if the push fails, it waits on the iPad and goes up with the next snapshot or ⬆ Push. Nothing else saves one. **🗂 Show past** (Live and Requests tabs) lists the snapshots, newest first; tap one to see it. The repo is public, so names and messages in a snapshot are readable by anyone (exact phone positions and phone ids are never saved)
- **🗂 Past gigs** — while nothing is published, the audience page lists past gigs (newest first, with date, place, image and song count) instead of just "Nessuna serata in corso". Tapping one shows its songs: people can heart the ones they liked and write a comment ("Com’è andata? Scrivici qualcosa", up to 200 characters, name optional). A gig gets there from **⬆ Upload** on a gig setlist, or from **📸 Snapshot live** (the songs opened in the chord reader in the last 12 hours, with the Gig & venue place and image). The Live tab's **🗂 Past gigs** box lists them with their hearts per song and comments (🗑 deletes a comment, ✕ removes a gig with its likes and comments, both after a confirm). While a gig is published but requests are closed, a **🗂 Le nostre serate passate** button at the very bottom of the audience page opens the same list (not while requests are open). Only you see the counts and comments. It needs the past-gigs rules from FIREBASE_SETUP.md (paste the rules again)
- **❤ Likes** — the audience can tap a heart next to any of the Now playing songs (the current one and the earlier ones shown), or next to any already played (✓ Suonata) song in the song lists, to like it, and tap again to take it back. The Live tab shows **❤ N** on each liked song in the setlist column (liked songs outside the setlist are listed under it), and the Likes box lists every liked song with its count, most liked first, plus the total, refreshed every minute while the tab is open (**↻** refreshes now); **Reset** sets them back to zero (Clear requests leaves them alone). It needs the `likes` rule from FIREBASE_SETUP.md (paste the rules again)
- **👀 Visits** — the Live tab shows how many phones opened the audience page: phones, visits, how many today and in the last hour, and when the last one came. A visit counts when a phone opens the page (or returns to it) at least 30 minutes after its last counted visit; refreshed every minute while the Live tab is open, **↻** refreshes now, **Reset** starts from zero (e.g. before a gig). It needs the `visits` rule from FIREBASE_SETUP.md (paste the rules again if you set Firebase up before)
- Only the published songs' titles and tags leave the app, never chords, keys or other data, and they go to a free Firebase database, not GitHub. One-time setup (about 15 minutes): see [FIREBASE_SETUP.md](FIREBASE_SETUP.md). Until it's set up, the rest of the app works exactly as before

### Data
- **Half-step down tuning** — a global header toggle for instruments tuned down a half step; moves every song's root key down a half step (back up when turned off). Chords and capo never change, and turning it on and off again leaves every song exactly as it was
- **Keyboard Mode** — a header toggle (device-local, not saved with the data) that relabels every "Capo" as "Transpose" throughout the app, for players who don't use a capo. Fret counts over 6 are shown wrapped an octave down as the equivalent negative shift (capo 7 → Transpose -5, capo 11 → Transpose -1) — the underlying saved value is unchanged, only the display
- All data stored in `localStorage` (persists across sessions on the same device)
- Each profile has its own data file in the repo, `repertoire_<profile>.json` (e.g. `repertoire_two_of_us.json`, `repertoire_loose_ends.json`), kept on a separate **`data` branch** so data pushes don't clutter the app's history on `main`
- On first load, seeds from the profile's file (read from the `data` branch through the GitHub API, no login needed) if no saved data exists
- Detects when the repo file differs from local data — comparing everything: every song field (chord sheet, Try out, Lyrics only, scroll speed…), setlists, tag colours and tuning — and offers to sync, saying how many songs/setlists differ
- **🔄 Refresh** — hard-reloads both the app itself and its data from the repo (`repertoire_<profile>.json` from the `data` branch, `index.html` from the published site), bypassing the browser cache on both — no GitHub login needed, replaces local data after a confirm
- **Confirmations** — anything that clears, resets, removes or deletes (songs, setlists, setlist rows and sections, alternates, profiles, requests, likes, visits, Now playing, the gig image, GitHub settings) asks first
- **Build stamp** — the bottom of the ⋯ menu shows "Build <date time>", so you can check after a Refresh that the latest version loaded
- **Export** — downloads current state as `repertoire_<profile>.json`
- **Import** — loads a previously exported JSON file
- **Push / Pull** — pushes the profile's `repertoire_<profile>.json` to the repo's `data` branch (or pulls it back) via the GitHub API
- **Profile switcher** — a header dropdown to jump between all available profiles (e.g. Two of Us / Loose Ends) without editing the URL by hand; its **✎ Edit profiles…** entry opens a popup to add a new one (starts empty — push to it once you've added songs) or delete one you no longer need

## Hosting on GitHub Pages

1. Push `index.html` (and `request.html`, the audience request page) to the `main` branch, and the `repertoire_<profile>.json` data files to a `data` branch (the app reads and writes them there via the GitHub API)
2. In the repo settings → **Pages** → set source to `main` / `root`
3. Access at `https://<username>.github.io/<repo>/`

The app works fully offline after the first load (localStorage persistence).
